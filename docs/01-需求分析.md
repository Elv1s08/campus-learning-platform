## 1 项目概述

### 1.1 项目背景

高校课程资料具有较强的校内属性与专业性，通用大模型在回答此类问题时缺乏课程资料依据，容易产生与教学内容不符的回答，且无法给出可核查的资料出处。本项目围绕这一痛点，建设一套面向校园场景的智能学习辅导平台：由教师维护课程知识库，学生基于知识库内容提问，系统返回带有资料来源的回答，并将问答过程沉淀为可统计的学习数据。

### 1.2 项目定位与技术边界

本项目**不是训练校园领域大模型**，而是基于成熟大模型服务，结合校内课程资料，采用 RAG（Retrieval-Augmented Generation，检索增强生成）技术实现可溯源的智能问答系统。该边界需要在答辩时明确说明。

系统的核心价值体现在三个方面：

1. **知识可控**：回答内容限定在教师上传的课程资料范围内，降低通用模型的幻觉风险。
2. **来源可溯**：每条回答附带引用的文档与知识块，学生可回溯原始资料。
3. **过程可度量**：问答行为被完整记录，形成学科热度、高频问题、学习活跃度等统计数据。

### 1.3 建设目标

| 目标类别 | 具体目标 |
|---|---|
| 功能目标 | 完成学生、教师、管理员三端核心业务，形成"建库—提问—回答—溯源—统计"完整闭环 |
| 技术目标 | 完成后端 REST 服务、关系型数据持久化、文档解析与向量化、RAG 问答、权限控制 |
| 质量目标 | 系统可本地一键启动、可稳定演示、异常场景有降级提示 |
| 文档目标 | 形成需求分析、数据库设计、接口设计、系统架构四类设计文档，支撑论文撰写 |

## 2 用户角色定义

系统设置三类角色，通过用户表中的角色字段区分，不引入复杂 RBAC 权限模型。

| 角色 | 标识 | 角色说明 | 主要诉求 |
|---|---|---|---|
| 学生 | `STUDENT` | 平台的最终使用者 | 基于课程资料提问、查看回答来源、管理错题与学习记录 |
| 教师 | `TEACHER` | 知识库的建设者与学情观察者 | 上传维护课程文档、查看所授学科学生的问答情况 |
| 管理员 | `ADMIN` | 平台的运营管理者 | 维护用户与学科、发布公告、审核内容、查看平台数据 |

## 4 功能优先级划分

原始需求清单覆盖面较广，全部实现会显著拉长周期并增加演示风险。按"能否支撑答辩"为标准划分为三个优先级。

### 4.1 第一优先级（必须完成）

该部分缺失将直接影响答辩，需完整、稳定实现。

**学生端**：注册登录、个人信息管理、学科选择、AI 对话、历史会话管理、回答来源展示、错题本收藏。

**教师端**：登录、学科知识库管理、上传 PDF/DOCX/TXT、查看文档处理状态、查看切分后的知识块、删除与重新解析文档、查看学生问答记录、简单学习统计。

**管理员端**：用户管理、学科管理、公告管理、平台基础数据看板。

### 4.2 第二优先级（时间允许再做）

题库管理、错题复习状态、学习记录统计、学习报告、教师辅导标记、消息通知、问答内容审核、Excel 报表导出。

### 4.3 第三优先级（仅设计不实现）

自动生成个性化学习计划、多模型动态切换、复杂实时消息系统、知识图谱、智能组卷、模型微调、多节点部署、自动化内容审核。

该部分以"系统展望"形式写入论文，不投入开发工作量。

## 5 核心业务流程

### 5.1 RAG 问答链路

系统技术难度集中在知识库的构建与检索链路，流程如下：

```text
教师上传课程文档 → 提取文档文字 → 切分知识块 → 生成向量 → 存入向量数据库

学生提出问题 → 问题向量化 → 检索相关知识块 → 知识块与问题组成提示词
             → 调用大模型 → 返回回答与资料来源 → 保存引用关系
```

业务数据存放于 MySQL，知识块向量存放于 Qdrant。两者通过 `knowledge_chunk` 表中记录的向量 ID 建立对应关系。

### 5.2 第一版业务闭环

第一版只实现一条核心链路，用于验证系统可行性并支撑答辩演示：

```text
管理员创建用户与学科
        ↓
教师上传课程文档
        ↓
系统解析文档并建立知识库
        ↓
学生基于知识库提问
        ↓
系统返回回答并展示引用来源
        ↓
教师查看学生问答记录与统计
```

### 5.3 第一版暂不实现的功能

复杂消息通知、自动生成学习计划、智能组卷、模型微调、知识图谱、微服务架构、Redis 与 RabbitMQ 中间件、复杂审核流程。

## 6 非功能需求

| 类别 | 需求描述 |
|---|---|
| 性能 | 普通管理类接口响应时间在 500ms 以内；AI 问答采用 SSE 流式输出，首字响应时间取决于模型服务 |
| 安全 | 用户密码使用 BCrypt 加密存储；模型密钥等敏感配置通过环境变量注入，不入库、不写死在代码中 |
| 兼容性 | 后端基于 Java 17 构建；前端适配主流 Chromium 内核浏览器 |
| 可靠性 | 模型服务不可用时给出明确降级提示，不抛出未捕获异常 |
| 易用性 | 系统可在本机通过少量命令完成启动，答辩现场可离线演示已有问答记录 |
| 可维护性 | 统一接口返回结构、统一异常处理、分层清晰，模块按业务域划分 |
| 数据规模 | 面向课程级知识库，单学科文档量级在数十至数百份 |

## 8 待确认的设计决策

以下事项需在数据库设计与接口设计阶段确定，并形成书面结论：

| 序号 | 待决问题 | 影响 |
|---|---|---|
| 1 | 学生是否可以自行注册，或仅由管理员开号 | 注册接口设计与用户状态流转 |
| 2 | 教师可管理的学科范围如何界定 | 是否需要 `teacher_subject` 关联表 |
| 3 | 上传文档是否需要管理员审核后入库 | 文档状态字段与审核流程 |
| 4 | 回答来源展示文档名、页码还是知识块原文 | `message_citation` 表字段设计 |
| 5 | 删除文档时是否同步删除向量库数据 | 删除逻辑与向量库一致性 |
| 6 | 学生之间是否可见彼此的问答记录 | 查询范围与权限校验 |
| 7 | 错题本是否区分学科 | 错题表结构设计 |
| 8 | 大模型服务选型与调用方式 | 配置文件结构与降级策略 |

## 9 AI 效果评价方法

为使论文具备实验与结果分析，而非仅呈现一套管理系统，设计如下对比评价方案：

**实验设计**：准备 20～30 道课程相关问题，分别采用两种方式获取回答。

- 对照组：直接调用大模型，不注入课程资料。
- 实验组：采用 RAG 方式，注入课程知识块后调用大模型。

**评价指标**：

| 指标 | 说明 |
|---|---|
| 回答正确率 | 回答内容与课程资料一致的题目占比 |
| 引用正确率 | 引用来源确实支撑回答内容的题目占比 |
| 检索命中率 | 检索到的知识块与问题相关的题目占比 |
| 平均响应时间 | 从发起提问到完整返回的平均耗时 |
| 教师主观评分 | 由教师对回答质量进行评分 |

该实验结果可直接作为论文中系统效果分析章节的数据来源。
